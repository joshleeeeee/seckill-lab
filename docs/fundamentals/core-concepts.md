# 核心概念讲解

如果你是第一次接触秒杀系统，这篇文章可以当成一节**先导课**。你不需要先懂所有分布式理论，也不用背术语；你只需要顺着一条问题线看下去：为什么会错、为什么会慢、为什么改完之后会更稳。

读完这篇后，你应该能做到**两件事**：第一，知道每个核心概念到底在解决什么问题；第二，知道这些概念会在哪个 lab 阶段真正落地。

本文默认你**还没有开始任何 lab**。你现在先建立概念框架，后续做 lab 时再回到这里对照，会更容易看懂每次改动到底在补哪一块能力。

## 怎么读这篇（适合还没做 lab 的你）

你可以按这个节奏读：

1. 先理解“问题是什么”（为什么会超卖、为什么会重复下单）。
2. 再理解“概念在解决什么”（原子性、幂等、补偿等）。
3. 最后记住“后续会在哪个 lab 落地”。

这样你开始做实验时，不会只是在抄命令，而是知道每一步背后的目的。

## 先把秒杀想象成一个现实场景

你可以把秒杀理解为“10000 个人在同一秒抢 100 个座位”。这个时候系统不是在处理“复杂业务规则”，而是在处理“极端同时到达的请求”。

这会立刻带来两个矛盾。第一个矛盾是 **速度（吞吐）** ：系统扛不住，就会排队、超时甚至雪崩。第二个矛盾是**正确性**：系统如果只追求快，很容易把 100 个座位卖成 120 个，也就是我们常说的超卖。

所以秒杀系统真正考验的不是某个框架 API 会不会用，而是你能不能在高并发下**同时守住吞吐和正确性**。

## 为什么第一个版本要“故意写得不安全”

很多同学在开始 `v0` 之前会问：既然它会出错，为什么还要这样写？答案很简单：教学里最怕“只讲正确答案，不讲错误是怎么来的”。

你在后续 `v0` 会看到一种写法：“先读库存，再扣库存”。单线程看没问题，并发下一定会暴露竞态条件。两个请求可能都看到库存为 1，然后都扣减成功，最后库存变成负数。这个错误不是代码语法错，而是时间顺序错。

你应该 **先亲手看见错误，再理解优化方案**，否则后面的方案只会变成抽象术语。

**后续对应 lab**：`v0 - 朴素同步秒杀`（[docs/chapters/v0-naive.md](../chapters/v0-naive.md)）

## 原子性：不是“快一点”，而是“不能拆开”

初学者最容易误解的一点是：我用了 `AtomicInteger`，是不是就安全了？答案是否定的。`AtomicInteger` 只能保证“某一次加减操作”是原子的，但不能保证“先校验再扣减这整个业务流程”是原子的。

你可以这样理解：你把门锁得很牢（单个操作安全），但门和窗户之间有空隙（流程有时间窗口），小偷还是能进来。秒杀里的原子性，要求的是**“校验库存 + 扣减库存”必须在一个不可分割的动作里完成**。

这个概念在 v0 会先以反例出现，在 v2 会通过 Redis + Lua 看到更工程化的落地方式。

**后续对应 lab**：v0（反例观察）-> v2（原子扣减实现，规划中）

## 一人一单：业务判断只是第一层，数据库约束才是兜底

先把定义说清楚：这里的“一人一单”指的是**同一个活动内，同一个用户最多只允许成功创建一笔订单**。它不是“全站只能买一次”，而是以活动为边界的购买上限策略。

为什么秒杀里常见这条规则？因为库存稀缺时，系统要优先保证公平和抗刷能力：限制同一用户反复抢购，避免少数账号快速囤货；同时也能降低“重复点击、网络重试”造成的重复订单风险。业务上当然可以改成“一人 N 单”，但底层并发控制思路是一致的。

很多项目里会写类似“如果这个用户下过单就拒绝”的判断。问题是并发场景下，两个请求可能在同一时刻都通过这个判断，然后都写进数据库。

所以“一人一单”不能只靠应用层 if 判断，必须有数据库唯一索引兜底（常见就是 `UNIQUE(activity_id, user_id)`）。真正可靠的做法是**双保险：应用层先挡一遍，数据库再做最终裁决**。

**后续对应 lab**：v1（唯一约束与一人一单）

## 乐观锁：让并发更新“冲突可检测”

乐观锁的核心思想是：我不先把资源锁死，而是更新时检查版本号是否还是我看到的那个版本。如果版本变了，说明期间有人先改过，我这次更新就失败，然后决定是否重试。

这套机制的好处是吞吐通常比重锁更友好，但它并不万能。冲突高的时候，失败重试会变多，数据库压力也会上来。它是一个**平衡工具**，不是一次性终结问题的银弹。

**后续对应 lab**：v1（库存乐观锁扣减）

## 为什么会有 Redis：因为数据库不是用来硬扛洪峰的

秒杀里最热的数据通常是库存。把每次库存校验都直接打到数据库，会很快把数据库拖进高争用状态。Redis 的价值在于把这条热点链路前置出去，用更轻量的方式承接高频读写。

但只用 Redis 还不够，还需要把校验和扣减放进 Lua 脚本里一次完成，避免并发窗口。你可以把它理解为：不仅把库存搬到快车道，还要确保这条快车道上的动作是**“一脚油门到底”的原子动作**。

**后续对应 lab**：v2（Redis 预热 + Lua 原子扣减）

## 为什么还要 MQ：因为再快也扛不住无限同时写库

当流量在同一秒爆发时，哪怕前面挡住了一部分，后面的下单写库仍然会形成尖峰。MQ 的作用是把**“瞬时洪峰”变成“可控吞吐”**。

你可以把它想成医院急诊分诊：不是让所有人同时冲进手术室，而是先排队，再按系统可处理速度推进。这样系统从“可能瞬间打穿”变成“可预测地变慢但不崩”。

**后续对应 lab**：v3（异步下单与削峰）

## 幂等：重试是常态，不是异常

网络抖动、客户端超时、消息重复投递，都会让同一个请求被执行多次。如果系统没有幂等设计，多执行一次就可能多一笔订单。

幂等不是“防用户连点”这么简单，它要覆盖同步接口和异步消费者两条链路。只做一头，另一头一样会漏。你后面会看到：真正稳的系统，不怕重试，因为它从设计上就把**“重复到达”当作常态**。

**后续对应 lab**：v4（请求幂等与消费去重）

## 最终一致性：允许短暂不一致，但不允许长期错误

秒杀系统通常会同时用 Redis、数据库、MQ。多组件协作意味着某个时刻出现短暂不一致几乎不可避免，比如库存先扣了但订单还在队列里没落库。

成熟系统的目标不是“任何时刻都强一致”，而是**“最终一致”**。也就是通过重试、对账、补偿，把短暂分叉收敛回正确状态。没有补偿能力的系统，偶发异常会慢慢积累成长期脏数据。

**后续对应 lab**：v5（超时关单、回补、对账补偿，规划中）

## 风控与限流：不是可选项，而是秒杀系统的一部分

很多教学项目只讲性能，不讲攻击流量，这是不完整的。真实秒杀场景里，机器脚本、刷子流量、异常重放请求都很常见。你不做限流和风控，系统可能不是被正常用户打垮，而是被异常流量拖垮。

**后续对应 lab**：v6（防刷、限流、风控策略，规划中）

## 可观测性：没有指标，就没有“优化”这回事

最容易自我欺骗的一点是：改完代码感觉更好了。工程里 **“感觉”不算证据**。你必须能回答：超卖是不是下降了？重复下单是不是减少了？排队延迟是否可接受？最终对账差异是否收敛？

只有当指标前后可对比，优化才成立。否则就只是“改了很多代码”。

**后续对应 lab**：v7（指标、看板、告警，规划中）

## 拆分微服务是最后一步，不是第一步

很多人一上来就想拆服务，这是常见误区。单体阶段如果连库存正确性、幂等、补偿都没闭环，拆成微服务只会把问题扩散到更多进程里。

正确顺序是**先把核心链路打稳，再考虑边界拆分**和团队协作效率。架构升级应该服务于问题，而不是追时髦。

**后续对应 lab**：v8（可选服务拆分与迁移策略，规划中）

## 你可以带走的一条主线

如果只记一条线，请记这条：

**`流量治理 -> 库存正确性 -> 异步化 -> 幂等 -> 补偿 -> 可观测`**

当你后续做每个 lab 时，都可以问自己：它是在补这条链路的哪一环。只要这条链路能闭环，系统就会从“能跑”走向“可用、可证、可演进”。
