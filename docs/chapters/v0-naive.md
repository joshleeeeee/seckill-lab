# v0 - 朴素同步秒杀：一次“看起来没问题”的并发翻车现场

你可能见过这样的线上事故：活动库存明明只有 50，最终却卖出了 60；用户只点了一次，后台却出现了两条订单。更麻烦的是，代码审查时大家都说“逻辑没问题啊”。

`v0` 这章就是把这类事故完整复刻出来。它是教学里的“故意不安全版本”：目标不是立刻修好，而是先把错误稳定复现，再把根因说透。只有先看见问题是怎么发生的，后面的优化才不是背答案。

[前置知识快读](../fundamentals/prerequisites.md) 和 [核心概念讲解](../fundamentals/core-concepts.md)。

这章难度是入门，预计 30 到 45 分钟。完成标准也很直接：你能复现并解释“超卖 + 重复下单”，并说清楚 v1 最先该补哪两条保障能力。

## 故障现场：第一轮压测，让问题自己出现

先把活动重置到干净状态：

```bash
# 重置活动库存到 50，保证本轮实验起点一致
curl -X POST "http://localhost:8080/api/v0/activities/1001/reset?stock=50"
```

预期会看到 `success=true`，并且 `remainingStock=50`。

然后直接打一次突发流量：

```bash
# 发起 300 请求、60 并发，快速制造竞态窗口
bash scripts/burst.sh v0 1001 300 60
```

这里 `300` 是总请求数，`60` 是并发度。

最后查快照：

```bash
# 读取本轮实验快照，验证是否出现超卖与重复下单
curl "http://localhost:8080/api/v0/activities/1001/snapshot"
```

如果 `oversoldUnits > 0`，说明发生了超卖；如果 `duplicateUserCount > 0`，说明发生了重复下单；如果 `remainingStock < 0`，说明库存已经被扣成负数。到这里，事故现场基本完整了。

## 根因拆解：错误不是“语法错”，而是“时间顺序错”

`v0` 的风险不是藏在复杂框架里，而是写在一条很常见的业务流程里：先看库存，再扣库存。这在单线程下没问题，在并发下就会出事。

你可以按这条时间线想象：请求 A 和请求 B 几乎同时进来，都读到库存是 `1`，都通过了“还能买”的判断。随后 A 扣减成功，库存到 `0`；B 继续扣减，库存到 `-1`。两个请求都“按规则执行”，但规则本身不是原子流程，于是系统得到一个错误结果。

这也是为什么 `AtomicInteger` 并不能兜住整个链路。`get()` 和 `decrementAndGet()` 各自是线程安全的，但“先判断再扣减”是跨两步的业务动作，中间天然有并发窗口。你锁住了单个动作，并没有锁住整段业务因果。

在实现上，`v0` 有四个故意保留的风险点：库存只在内存里（`AtomicInteger`），下单是两步流程，没有“一人一单”唯一约束，也没有请求幂等/消费去重。对应代码可以直接看 `seckill-app/src/main/java/com/seckill/lab/stage/v0/service/V0NaiveSeckillService.java`。

## 再下钻一层：从 Java 代码到 OS 调度

如果你想把这个问题彻底吃透，必须往下看到 OS 这一层。`v0` 默认跑在 Spring Boot + Tomcat 模型下，一个 HTTP 请求通常对应一个工作线程（例如 `http-nio-8080-exec-*`）。这些线程最终都是 OS 可调度实体，谁先跑、谁被抢占、何时恢复，不由业务代码决定，而由内核调度器决定。

也就是说，哪怕你的代码只写了两行“先判断、再扣减”，在 CPU 看来它们之间可以被任意切开。Linux 调度器在时间片到期、线程阻塞/唤醒时都可能发生上下文切换。一次上下文切换会保存当前线程的寄存器和程序计数器，再让另一个线程继续执行。并发 bug 就藏在这个“可被切开的缝”里。

把超卖翻车过程按 OS 视角重排，大概是这样：

```text
# 线程 T1 处理请求 A，先通过库存判断
T1: read stock = 1, check pass

# OS 抢占 T1，切到线程 T2 处理请求 B
T2: read stock = 1, check pass
T2: decrementAndGet -> 0

# OS 切回 T1，T1 已经通过旧判断，不会自动回滚
T1: decrementAndGet -> -1
```

注意这里不是“可见性问题”，而是典型的 TOCTOU（time-of-check to time-of-use）问题：检查发生在前，使用发生在后，中间存在调度窗口。

很多人会问：既然用了 `AtomicInteger`，为什么还会这样？因为 `AtomicInteger` 只保证单个更新动作的原子性，它的底层是 CAS（compare-and-swap）循环，本质上只对“这一次写入”负责，不对“两步业务流程”负责。可以把它理解成下面这段示意代码：

```java
// 示意：CAS 只保证一次变量更新原子，不保证前后业务判断原子
for (;;) {
    int current = getVolatile();
    int next = current - 1;
    if (compareAndSet(current, next)) {
        return next;
    }
}
```

这段循环再安全，也无法替你表达“只有在我刚刚检查库存>0这个前提仍成立时，才允许扣减”这个跨步骤业务约束。这就是 v0 的本质缺陷：单操作线程安全，不等于业务流程正确。

同理，“同一用户重复下单”在 OS 视角下也很好理解：两个线程可能几乎同时处理同一 `userId` 请求，在没有数据库唯一约束的情况下，它们都能一路通过并写入成功。线程安全集合解决不了业务唯一性，最终还是需要约束系统（下一章的唯一索引）来做裁判。

## 现场里最容易踩的三个认知陷阱

很多人第一次复盘会被三个错觉带偏。第一个错觉是“库存不为负就没事”，但重复下单同样是业务错误；第二个错觉是“压测一次没复现就代表安全”，并发问题天然带概率性，没复现不等于不存在；第三个错觉是“计数器线程安全就等于链路正确”，单点线程安全和流程一致性根本不是一回事。

## 局限与下一步：v0 的价值到这里就结束了

`v0` 的局限非常明确：它能帮助你看见并发错误，但并不提供数据库级正确性保障。只要流量上来，超卖和重复下单都可能发生。

所以下一章 `v1` 会做两件最优先的事：加入一人一单唯一约束，以及基于乐观锁的库存正确扣减。到那一章，你会把这次“故障现场”的每一个现象，和具体改造点一一对上。

如果你现在能稳定复现 `oversoldUnits > 0` 或 `duplicateUserCount > 0`，能用时间线解释竞态窗口，并能说出 v1 的两项优先能力，那这章就算真正过关了。
